# Multi-Agent Development Orchestrator 知識ベース & 設計原則 (MEMORY.md)

本ドキュメントは、プロジェクト「`mag` (Multi-Agent Development Orchestrator)」の設計意図、重要な意思決定履歴（ADR）、およびAIが遵守・学習すべき基本原則を記録します。

---

## 🧭 開発時の5大原則 (Core Principles)

### 原則1: 最初から完全自動化しない
- いきなり高度な自律AIループを構築しようとせず、まず **「Manager → Worker → Result」の確定的な基盤通信と実行制御** を確実に動かす。
- ルールベースおよびダミータスクで堅牢性を担保してから、LLMによるタスク分解・生成・レビューを段階的に導入する。

### 原則2: AIよりも実行基盤を先に安定させる
- コンテナ環境、REST API、Git Worktree、ログ管理機構、DB永続化が安定して初めて、AIエージェントが安全に機能する。
- 実行基盤の脆さはAIの幻覚（Hallucination）や暴走の最大の要因となる。

### 原則3: Agentに無制限の権限を与えない
- 各Agentは最小権限の原則（PoLP）に従い、コンテナ隔離と権限ホワイトリストで被害範囲を厳格に限定する。
- ファイル一括削除（`rm -rf`）や環境破壊の恐れがあるコマンドは、必ず人間（User）の承認プロンプトを挟む。

### 原則4: Agentの出力を必ず構造化する
- Agent間の連携・判定を自然言語（フリーテキスト）だけに依存させない。
- すべてのWorkerは、明確に定義されたJSONスキーマ（`status`, `task_id`, `summary`, `files_changed`, `tests`, `errors`, `commit`等）で結果を返す。

### 原則5: すべての作業をログに残す
- 「誰が（どのAgentが）」「いつ」「何を」「なぜ」実行したかを、追跡可能なログ（`logs/manager.log`, `logs/tasks/TASK-xxx.json`）として完全に永続化する。

## 🏛️ アーキテクチャ上の重要決定 (ADR)

### ADR-001: 実行環境の2ノード分離
- **決定**: 親ノード（Ubuntu 26.04）とWorker実行ノード（Ubuntu 24.04）を分離する。
- **理由**:
  - Manager（プロジェクト管理・Git・タスク統括）を保護し、不安定なWorkerプロセスやテスト実行環境からの干渉・クラッシュを防ぐ。
  - 将来的な分散ノードへのスケーリングを可能にする。

### ADR-002: 通信プロトコルに HTTP + JSON を採用 (MVP)
- **決定**: 初期通信方式として、gRPCやMessage Queueではなく、FastAPIによる HTTP/REST + JSON を採用。
- **理由**:
  - デバッグの容易性、軽量性、curl等での直接検証の容易性を最優先。
  - システム成熟後にWebSocketやRedis/MQへの移行を検討。

### ADR-003: 初期実装言語に Python を選定し、将来 Rust への移行を視野に
- **決定**: オーケストレーターおよびWorkerのMVP実装は Python (FastAPI, Pydantic, Docker SDK) で行う。
- **理由**:
  - 非同期API、Docker操作、LLM API呼び出し、JSON構造化のプロトタイピング速度を最優先。
  - コアデーモンが安定した段階で、高信頼性・単一バイナリ配布が可能な Rust (`mag` CLI) への移行を進める。

### ADR-004: Git Worktree による作業ディレクトリ分離
- **決定**: 共有ディレクトリを直接全Agentに触らせず、Git WorktreeとAgent専用ブランチを活用する。
- **理由**:
  - 同時編集によるファイル競合を物理的に防止。
  - テストやレビューが完了したブランチのみをManagerが安全にマージできる。

## 🛡️ 安全装置 & エラーハンドリングのベストプラクティス

1. **リトライ上限 (`MAX_RETRY = 3`)**:
   - 同一エラーでの無限修正ループを防ぐ。3回失敗した場合は `FAILED_PERMANENTLY` とし、人間にエスカレーションする。
2. **自己修復 (Self-Repair) ループ**:
   - ビルド失敗・テスト失敗時は、スタックトレースをDeveloper Agentにフィードバックしてピンポイント修正を行わせる。
3. **環境問題とコード問題の切り分け**:
   - 不明瞭なビルドエラー時は `envdoctor` を呼び出し、PATH・コンパイラ・ライブラリの整合性を確認する。
4. **Rustエラーの日本語診断**:
   - Rustプロジェクトにおけるエラー時は `jpcargo` 連携により、分かりやすいエラー解説をDeveloper Agentへ供給する。

## 💡 プロジェクトの差別化メモ
| 項目 | Multigravity型 (従来) | 本プロジェクト (mag) |
|---|---|---|
| 目的 | 複数アカウント/プロファイルの切り替え | 組織化された自律開発チームの運用 |
| 構造 | フラットな並行環境 | Manager統括による階層型DAG実行 |
| 検証 | 人間が手動でチェック | Tester / Reviewer / Security による自動多重検証 |
| 修復 | 人間が指示 | エラー分析に基づく自己修復ループ |
